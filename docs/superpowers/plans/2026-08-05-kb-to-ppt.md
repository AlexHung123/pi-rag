# KB → PPT Integration Plan

> **For agentic workers:** Execute task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let pi-rag users turn selected knowledge-base evidence into a downloadable, natively editable `.pptx`, without embedding the full ppt-master coding-agent workflow into the chat agent.

**Architecture:** Keep pi-rag as multi-user RAG chat. Add a **PptJob** pipeline: Agent (or UI) gathers RAG evidence → structured outline → async worker in a per-user isolated directory → export `.pptx` → authenticated download. Reuse **ppt-master scripts/templates** as a vendored worker toolbox; do **not** give the chat agent unrestricted shell/filesystem access.

**Tech Stack:** NestJS, Prisma/Postgres, existing pi-agent-core tools, optional Python worker (ppt-master scripts / python-pptx), React download UI.

**Related repos / references:**

- This product: `D:\Coding\pi-rag` (CSB Knowledge Base Portal)
- Design toolbox (do not monorepo-merge as app code): [hugohe3/ppt-master](https://github.com/hugohe3/ppt-master) — skill package under `skills/ppt-master/`
- Preferred first path: ppt-master **Quick Generate** profile (no Confirm UI / multi-stage design gates)
- Avoid first: full default Strategist → confirmation → Executor SVG pipeline inside SSE chat

**Non-goals (P0–P2):**

- Browser direct access to worker FS or RAGFlow
- Full ppt-master Confirm UI / live SVG editor inside pi-rag chat
- Arbitrary `run_shell` / write-anywhere tools on the domain chat agent
- Magazine-grade unconstrained SVG authoring as the default product path

## 1. Problem & product decision

### Problem

Users already retrieve and discuss private KB content in pi-rag. They often need a **汇报 deck**, not only chat answers. ppt-master can produce native DrawingML PPTX, but it is a **local coding-agent skill** (read/write/bash + multi-step gates). pi-rag is a **multi-tenant portal** with a constrained tool agent (`retrieve_chunks` / `keyword_search` / `list_document_chunks`).

### Decision (locked for this plan)

| Decision | Choice |
|----------|--------|
| Integration style | **RAG front-end + PPT backend job**, not “paste SKILL.md into chat agent” |
| Chat agent role | Intent, retrieval, outline/facts; **submit job** only |
| Generation runtime | Async **worker** with per-`userId`/`jobId` workspace |
| ppt-master role | Vendored **scripts + templates** (submodule or pinned copy), not Nest business logic |
| MVP quality bar | Correct facts from RAG + usable editable PPTX; visual polish secondary |
| First generation path | **P1 fixed/simple template** → **P2 quick/export tooling** → **P3 optional full design desk** |

```text
User selects KBs → chat: "做一份 PPT"
        │
        ▼
┌───────────────────┐
│ pi-rag Agent      │  retrieve_* → evidence
│ (existing tools)  │  draft outline JSON
│ + create_ppt_job  │
└─────────┬─────────┘
          │ enqueue
          ▼
┌───────────────────┐
│ PptService/Worker │  data/ppt-jobs/<userId>/<jobId>/
│ Python + scripts  │  sources/ outline/ svg_output?/ exports/
└─────────┬─────────┘
          │
          ▼
   Authenticated download  exports/*.pptx
```

## 2. Architecture principles

1. **NestJS remains the only public API** — same as existing isolation model.
2. **Ownership everywhere** — list/get/download PPT jobs by `owner_user_id`; cross-user → 404.
3. **No free-form coding tools on chat agent** — only domain tools (`draft_ppt_outline`, `create_ppt_job`, `get_ppt_job_status`).
4. **Facts from RAG only** — numbers, clauses, product claims must come from retrieved evidence; design/layout may use the model.
5. **Async by default** — HTTP/SSE must not block on multi-minute SVG generation.
6. **Hard limits** — max pages, max concurrent jobs per user, wall-clock timeout, disk quota per job.
7. **Worker sandbox** — cwd = job directory; allowlist of Python entrypoints; no access to other users’ trees or host secrets beyond env.

## 3. Workspace & vendor layout

### Job directory (runtime)

```text
data/ppt-jobs/<userId>/<jobId>/
  meta.json              # status, options, conversationId, timestamps
  sources/               # evidence.md, optional user uploads
  outline.json           # page plan + citation anchors
  notes/                 # optional per-page notes (later)
  svg_output/            # only if using SVG pipeline (P2+)
  exports/               # final .pptx
  logs/                  # worker stdout/stderr tail
```

`data/ppt-jobs/` is gitignored; production may use object storage for `exports/` only.

### Vendoring ppt-master (choose one in Task 0)

| Option | When |
|--------|------|
| A. `git submodule` at `vendor/ppt-master` | Want upstream pulls |
| B. Pin-copy `skills/ppt-master/scripts` + needed `templates/` + `requirements` | Smaller, locked version |
| C. Docker image with Python + deps; mount job dir | Cleaner prod isolation |

**Do not** ship the full icon library into `apps/web` build.

## 4. Data model (Prisma)

```prisma
enum PptJobStatus {
  queued
  gathering
  generating
  ready
  failed
  cancelled
}

model PptJob {
  id               String       @id @default(uuid())
  ownerUserId      String
  conversationId   String?
  status           PptJobStatus @default(queued)
  title            String?
  /// Selected app KB UUIDs
  knowledgeBaseIds String[]     @default([])
  /// User/agent options: pageCap, locale, theme, templateId
  optionsJson      Json         @default("{}")
  /// Structured outline (pages, bullets, citation indices)
  outlineJson      Json?
  /// Denormalized error for UI
  errorMessage     String?
  exportRelPath    String?      // relative under job root
  pageCount        Int?
  createdAt        DateTime     @default(now())
  updatedAt        DateTime     @updatedAt
  startedAt        DateTime?
  finishedAt       DateTime?

  owner User @relation(fields: [ownerUserId], references: [id], onDelete: Cascade)

  @@index([ownerUserId, createdAt])
  @@index([status, createdAt])
}
```

Adjust field names to match existing Prisma style in `apps/api/prisma/schema.prisma`.

## 5. API surface

| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/api/ppt/jobs` | Create job (body: kbIds, title, options, optional outline, conversationId) |
| `GET` | `/api/ppt/jobs` | List current user’s jobs |
| `GET` | `/api/ppt/jobs/:id` | Status + outline summary |
| `GET` | `/api/ppt/jobs/:id/download` | Auth download of `.pptx` (404 if not ready / not owner) |
| `POST` | `/api/ppt/jobs/:id/cancel` | Best-effort cancel if still queued/generating |

All routes: session auth + ownership checks (same pattern as knowledge/chat).

### Agent tools (extend `agent.tools.ts`)

| Tool | Description |
|------|-------------|
| `draft_ppt_outline` | From selected KBs: retrieve (or reuse turn evidence) → return outline JSON + citation map; **does not** start export |
| `create_ppt_job` | Persist job + enqueue worker; params: title, knowledgeBaseIds, pageCap, locale, optional outline override |
| `get_ppt_job_status` | Status, error, download readiness for a job id owned by user |

Update `DOMAIN_SYSTEM_PROMPT`:

- When user asks for PPT/slides/deck: retrieve first → outline → `create_ppt_job`.
- Never invent KB facts; cite evidence indices in outline bullets where possible.
- After job creation, tell user job id and that download appears when status is `ready`.

## 6. Worker pipeline

### P1 — Template fill (MVP export)

1. Load `outline.json` + `sources/evidence.md`.
2. Render with **fixed layouts** (title / section / bullets / two-column / closing) via `python-pptx` **or** a minimal ppt-master export path if already simple enough.
3. Write `exports/<slug>.pptx`.
4. Mark job `ready` or `failed`.

### P2 — ppt-master quick path

1. Materialize ppt-master-like project tree under job dir.
2. Write sources from RAG evidence (no silent fact invention).
3. Run allowlisted commands only, e.g.:
   - `python vendor/ppt-master/skills/ppt-master/scripts/...` (exact entrypoints TBD when wiring)
4. Prefer **quick / non-interactive** profile semantics: no Confirm UI, hard page cap, timeouts.
5. Quality gate optional: size checks, file exists, open with python-pptx smoke read.

### P3 — Full design desk (optional product)

Separate UI route “PPT 工作台” with multi-step confirmation — **out of chat SSE**. Only after P1/P2 prove demand.

### Process model

| Phase | Implementation choice |
|-------|---------------------|
| Dev | In-process async queue or `setImmediate` worker loop |
| Prod | Separate Node/Python worker process or container; Postgres `status=queued` as queue |

## 8. Security, limits, observability

| Control | Initial default (tunable via env) |
|---------|-----------------------------------|
| `PPT_MAX_PAGES` | 12 |
| `PPT_MAX_JOBS_PER_USER` | 3 active (`queued`/`gathering`/`generating`) |
| `PPT_JOB_TIMEOUT_MS` | 15–30 min depending on path |
| `PPT_MAX_CONCURRENT_GLOBAL` | 2–4 workers |
| Path traversal | Resolve all paths under job root; reject `..` |
| Download | Owner-only; short-lived signed URL optional later |
| Logging | job id, user id, duration, page count, failure reason — no raw KB dump in logs |

## 11. Acceptance criteria

### P1 done when

1. Logged-in user with selected KBs can create a PPT job.
2. Outline bullets are traceable to retrieval (no fabricated clause numbers in happy path).
3. User can download a `.pptx` that opens and is element-editable.
4. Another user cannot list/download the job (404).
5. Limits prevent runaway concurrent generation.

### P2 done when

1. Feature-flagged worker produces PPTX via ppt-master quick-style pipeline for the same outline/sources.
2. Worker cannot read other users’ job directories.
3. Failures are visible in API/UI with non-secret error messages.

## 12. Risks & mitigations

| Risk | Mitigation |
|------|------------|
| Full SVG agent too slow/expensive in multi-tenant API | Ship template export first; cap pages; async queue |
| Chat agent given bash → data leak | Never add unrestricted shell; domain tools only |
| ppt-master upstream churn | Pin submodule commit or vendor copy |
| Model invents facts in slides | Outline + export copy only from evidence fields; prompt + schema |
| Long jobs + pool agent TTL confusion | Jobs independent of `AgentSessionPool`; status in Postgres |
| Windows vs Linux worker paths | Normalize paths; prefer Linux container for worker in prod |

## Appendix B — Explicit anti-patterns

1. **Do not** run full ppt-master `SKILL.md` routing inside the existing chat `Agent` with host cwd = monorepo root.
2. **Do not** mount the entire developer `D:\Coding\ppt-master` tree as a shared writable volume for all tenants.
3. **Do not** block `POST /messages` SSE until PPTX finishes.
4. **Do not** treat “make it look like the best ppt-master examples” as P1 scope.
